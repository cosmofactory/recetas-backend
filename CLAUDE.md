# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project context

**recetas-backend** is the production backend for a public, non-profit website about Spanish cuisine. It's a modular Go monolith: one binary, one Postgres. `main` is protected and must always be releasable. Deploys to the demo and prod environments come back in INF-2 (see CI/CD below).

Write the code a senior Go engineer would ship. Don't add teaching comments, "Concept" notes, or comparisons with Python/SQLAlchemy/Alembic to code, plans, or commits. The `docs/plans/` documents were written as learning material while the project was a sandbox. Treat them as history: they describe how the current code came about, but their scope limits (e.g. "no tests, no structured logging") no longer apply.

## Architecture

- **Domain modules** live in `internal/<module>/`. Today there's one, `catalog` (regions, dishes with flags, one variation per dish×region, one recipe per variation, slug keys; the model is defined by the design handoff and `../CLAUDE.md`, the schema in `docs/schema.md`). Besides its sqlc package `catalogdb` and the test-only fixture loader `catalogtest` (`Load(t, tx)` inserts one complete catalog in en/es/ru), it has these layers:
  - `catalog.go`: domain types (no JSON tags; the HTTP shapes are the generated `apigen` types) and the `Repository` interface. `errors.go`: the sentinel `ErrNotFound` and `*MissingTranslationError` (entity, key, locale).
  - `repository.go` + `mapping.go`: `NewPGRepository(catalogdb.DBTX)` on the sqlc `Queries`, mapping rows to domain types and `pgx.ErrNoRows` to `ErrNotFound`. Queries LEFT JOIN the translations (plus the `es` row a second time for `nameEs`); a NULL means a missing row, returned as `*MissingTranslationError` with no fallback (D-BE3-3). Query counts are fixed: regions 2, dishes 2 (all variations in one query), recipe 3, plus the service's content-version read on every request (`docs/perf-baseline.md` has the per-request span counts for the N+1 check). `ContentVersion` is 0 before the first import.
  - `service.go` + `memo.go`: reads the content version on every call and memoises the assembled region and dish lists per (locale, version); storing a newer version evicts older ones and failed loads aren't stored. `Region`/`Dish` are answered from those lists, `Recipe` goes to the repository.
  - `handler.go` + `response.go` + `etag.go`: `NewHandler(svc, logger)` implements `apigen.StrictServerInterface`. It defaults a missing `lang` to `en`, answers a key that fails the contract's slug pattern with 404 before any query, maps `ErrNotFound` to 404 `not_found` and anything else to a generic 500 `internal` (logged once at Error with `err`), and sets `ETag` (`W/"<version>-<locale>"`, recipes `W/"<version>-<locale>-<dish>-<region>"`) and `Cache-Control: public, max-age=60, stale-while-revalidate=600`.
- **API contract.** `api/openapi.yaml` (OpenAPI 3.0.3) is the source of truth for the public `/v1` API (spec-first: change the spec, then `make api-generate`). oapi-codegen writes models, the std-http router and the strict-server interface to `internal/api/apigen/`; never hand-edit it. `internal/api` adapts that interface: `Register(mux, impl, logger)` wires the catalog operations, `GET /openapi.json` (the embedded spec converted to JSON once by `SpecJSON`; `main.go` fails fast if it doesn't parse) and a `/` catch-all that returns the contract 404 (so a wrong method on a known path is 404, not 405). It validates the `lang` enum (the generated wrapper doesn't), maps parameter-binding errors to 400 `invalid parameter <name>` and handler errors to a logged 500. The catalog routes run through `httpx.ConditionalGET`, which buffers the response and turns a 200 into a bodyless 304 (keeping `ETag` and `Cache-Control`) when an `If-None-Match` value matches its ETag (weak comparison, comma lists on any number of header lines, `*`); the strict interface can't see request headers. `api.Stub` (501 for every operation) lives in a test file for the adapter's own tests. `/healthz` and `/openapi.json` are in the spec but excluded from codegen (`exclude-operation-ids`); they have their own handlers.
- **Error shape.** Every error response is `{"error":{"code":"...","message":"..."}}` (the spec's `Error` schema), written with `httpx.WriteError`. Codes: `bad_request`, `not_found`, `payload_too_large`, `internal`, `not_implemented`.
- **Content import** (`internal/catalog/importer`, `cmd/import`; the contract for the content pipeline is `docs/content-import.md`). A bundle (`api/content-bundle.schema.json`, embedded as `api.ContentBundleSchema`) is the full desired catalog. `Parse` checks it against the JSON Schema (santhosh-tekuri/jsonschema v6) and `Validate` checks the semantic rules; both return `*ValidationError` with every problem as an RFC 6901 pointer. `Apply(ctx, Beginner, Bundle, Options)` validates again, then in one transaction (a savepoint when given a `pgx.Tx`) takes an advisory lock, loads the stored catalog (`state*.go`), diffs it by natural key (`diff*.go`: regions/dishes by key, variations/recipes by `recipeKey`; a variation moved to another dish or region is deleted and recreated) and writes it (`write*.go`: deletes first, then sort orders that change are negated before rows are written so the UNIQUE `sort_order` never collides; translations upserted, regional dishes, time notes, ingredients and steps replaced by position). It always compares with the database (so a re-import repairs drift); a plan with no changes adds no content version, and `Checksum` (SHA-256 of the canonical JSON) is only recorded in `content_versions`. `Parse` rounds quantities to 3 decimals and rejects an unsupported `schemaVersion` first; a dry run rolls back and reports the unchanged version. Its sqlc queries are `db/queries/catalog/import_*.sql`. `cmd/import` (`/app/import` in the image) reads `--source` (required), `--file` or stdin, `--dry-run`; exits 0 ok, 1 usage/validation (before any DB access), 2 database. It reads only `DATABASE_URL` (plus `.env`), not `APP_ENV`, and connects lazily on the first `Begin`.
- **Wiring** happens only in `cmd/server/main.go` (and `cmd/import/main.go` for the import CLI, which passes a no-op tracer provider), which builds config → telemetry → logger (logs `starting` with `version`/`app_env`, and `telemetry disabled` when off, before touching the DB) → pgx pool → `catalog.NewPGRepository` → `catalog.NewService` → `catalog.NewHandler` → `api.Register`. It also handles graceful shutdown on SIGINT/SIGTERM within one 5s budget (`cmd/server/shutdown.go`): `gracefulShutdown(shutdownSteps)` drains the server with 4s (`drainTimeout`; `srv.Close` when the drain fails), then flushes telemetry with a fresh 1s context (`flushReserve`), then closes the pool; every step runs and their errors are joined. A startup or serve failure is logged first and then takes the same flush → close-pool path (`abort`), so every exit flushes once and closes the pool last. Modules never import each other.
- **Shared infrastructure** lives in `internal/platform/` (`database`: pgxpool bootstrap, `ParseConfig(Options)`/`NewPool(ctx, Options)` where `Options{URL, TracerProvider, Size}` and `Size` is a `PoolSize{MaxConns, MinConns}` that wins over any `pool_*` URL parameters (a zero `Size` means `DefaultPoolSize()`) (`DefaultPoolSize()`/`DefaultMaxConns`/`DefaultMinConns` are the one place the defaults live; config and `cmd/import` use them), with an otelpgx tracer that names spans `query <Name>`, `prepare <Name>` (pgx's statement cache, a child of the query span) or `batch query <Name>` from the sqlc `-- name:` comment, sets `db.operation.name` to the bare name, and never records arguments; `telemetry`: `Setup(ctx, cfg)` returns a TracerProvider, LoggerProvider and `Shutdown` exporting over OTLP/HTTP to `<endpoint>/v1/traces` and `/v1/logs` (`Authorization: <token>`, batch processors, resource `service.name`/`service.version`/`deployment.environment.name`), or no-op providers when `LOGFIRE_TOKEN` is blank; it never sets the OTel globals, so providers are injected; `RecordError(ctx, err)` adds an exception event to the request span and sets it to Error (no-op for a nil err); `logging`: `slog` JSON logger that adds `trace_id`/`span_id` when the context has a span and `request_id` when it has one (`WithRequestID`/`RequestIDFrom`), and `NewTee` that also bridges records to OTel via otelslog; `health`: `GET /healthz`, a 1s DB ping behind a `Pinger` interface, used by the Docker/compose healthcheck, the frontend's `/readyz` and uptime checks; `httpx`: hardened `http.Server` and the middleware chain `Stack(mux, logger, tp)`: 64 KiB body limit (outermost, so `MaxBytesReader` sees net/http's own writer and a 413 closes the connection) → `Trace` (otelhttp server span on `tp`, W3C `traceparent` only, no span for `/healthz`) → `RequestID` (honours an `X-Request-ID` of 1–64 `[A-Za-z0-9._-]`, else 32 random hex; echoed, set on the span, and put in the context through `logging.WithRequestID`, so every log line of the request, the access line included, carries `request_id`) → access log (a 2xx `/healthz` at DEBUG) → panic recovery (also recorded on the span) → 12s handler deadline (below the 15s `WriteTimeout`, so the error response still gets written) → `Routed(mux)`, which hands the matched route back to the access log and renames the span `METHOD /route` with `http.route`, even after a middleware clones the request) and `internal/config/` (env vars parsed by the pure `FromEnv(getenv)`; `Load()` first loads `.env` via godotenv when it exists).
- **SQL-first data access.** Migrations in `db/migrations/` (goose) are the schema source of truth. `sqlc.yaml` has one `sql` entry per module: it reads the migrations plus `db/queries/<module>/*.sql` and writes `internal/<module>/<module>db/` (today only `catalog` → `catalogdb`). Never hand-edit generated code. A new module gets its own entry, queries dir and output package, so generated code stays inside its module.
- **Migrations run at container start.** `docker/entrypoint.sh` runs `goose up` and then `exec`s the command (the server, or `/app/import` under `docker compose run`). In production, a migration is applied before the new binary takes over, while the previous container may still be serving. Keep migrations backward-compatible with the running release (expand/contract), and always write a working `-- +goose Down`.

## Configuration

`internal/config` (`FromEnv`) is the one place the server reads env vars; `.env.example` lists every variable with a comment and must stay in step with it.

- Server: `APP_ENV` (required, `local|demo|prod`), `LOG_LEVEL` (`debug|info|warn|error`, default `info`), `DATABASE_URL` (required), `HTTP_ADDR` (default `:8080`), `DB_MAX_CONNS` (pool size, default 10, 1–100) and `DB_MIN_CONNS` (default 1, 0–`DB_MAX_CONNS`; both trimmed, blank = default; 10 leaves most of Postgres' default `max_connections` of 100 for the import CLI and operators), `LOGFIRE_TOKEN` (blank = telemetry off, and nothing below is read), `OTEL_EXPORTER_OTLP_ENDPOINT` (required with a token, https) and `OTEL_SERVICE_NAME` (default `recetas-backend`). The SDK also honours `OTEL_TRACES_SAMPLER`/`_ARG` (default `parentbased_always_on`; no `WithSampler` is set).
- Import CLI: `DATABASE_URL` only, with the default pool size.
- Compose (`docker-compose.yaml`): `POSTGRES_DB`/`_USER`/`_PASSWORD`, `BACKEND_HOST_PORT`, `DB_HOST_PORT`, `DB_BIND_ADDRESS`, `VERSION` (build arg); it derives the container's `DATABASE_URL` and passes the server variables through.
- Tests: `TEST_DATABASE_URL` (integration tests; see Conventions) and `CI`.
- A new variable goes into `FromEnv` (with a `config_test.go` case), `.env.example`, the README's table, this section, `docker-compose.yaml` when the server reads it, and the INF-5 prod `.env` checklist.

## Operations

- `docs/runbook.md` is the backend runbook (INF-6's `RUNBOOK.md` links to it): logs and `request_id`/`trace_id` correlation, `/healthz`, imports, image and migration rollback (the per-migration Down costs from the BE-6 review: rolling back 00008 needs the image rolled back first and its `content_versions` rows saved before the down and restored before any import, because a same-bundle re-import is `no changes` and would leave the version at 0 and later reissue old ETags; going below 00008 needs a re-import after rolling forward), and failure modes. Keep it in step when behaviour it describes changes (log messages, health responses, exit codes, env vars). VM paths and compose names in it are as planned in INF-2/INF-5 until those exist. Every VM command names the project (`docker compose -p recetas-<env>`, prod also `--env-file .env --env-file versions.env`): a bare `docker compose` in `/srv/recetas/<env>` would use the directory name as the project, an empty stack.
- `docs/perf-baseline.md` records the demo baseline; `scripts/load/` produces it. The API isn't public and the frontend doesn't proxy `/v1`, so the API run happens from a k6 container on the demo Docker network, and the run through Caddy targets the frontend pages (`TARGET=pages`).
- Telemetry export failures don't affect requests: the OTel SDK's default error handler prints plain-text (non-JSON) lines to stderr, and shutdown logs `flush telemetry failed`.

## Conventions

- Module path: `github.com/cosmofactory/recetas-backend`. Go 1.27; dependencies are limited to pgx/v5, godotenv, and for the API contract kin-openapi (spec → JSON) and oapi-codegen/runtime (used by generated code), santhosh-tekuri/jsonschema/v6 (+ golang.org/x/text for its messages; the import's bundle schema), OpenTelemetry (the Go SDK, OTLP/HTTP exporters, otelhttp, otelslog and exaring/otelpgx: vendor-neutral traces and logs to Logfire, stack.md B7; otel v1.47 (log and sdk/log v1.47, otlploghttp v0.23), otelhttp v0.72, otelslog v0.21), and goose (test-only: the migration round-trip test in `db/`). Prefer the stdlib, and justify every new dependency.
- Every I/O function takes `ctx context.Context` as its first argument, and handlers pass `r.Context()`.
- Wrap errors with `fmt.Errorf("doing x: %w", err)` at each layer boundary. Use `errors.Is` against module sentinels instead of comparing strings. Don't panic in request paths.
- Log with `log/slog` only (JSON to stdout). The logger is built in `main.go` and injected through constructors; never use the `log` package or `slog`'s default logger. Unexpected errors log at Error with an `err` attr; client errors (4xx) don't log at Error.
- Never leak internal error text to clients. 5xx responses get a generic message, and the detail goes to the log.
- Panics are recovered by `httpx.Recover` into a generic 500 (stack goes to the log). The access log records the route pattern, never the raw path, query string or body. Handlers that decode a body map `*http.MaxBytesError` to 413.
- Handlers and services never touch `*pgxpool.Pool` or a `<module>db` package directly. Everything goes through the repository.
- Integration tests use `testdb.Tx(t)` (`internal/platform/testdb`), a transaction rolled back in `t.Cleanup`; they skip without `TEST_DATABASE_URL`. They never read `DATABASE_URL`, because `make test` loads `.env`, which points it at the dev DB. Don't assume an empty table: measure deltas or look up the rows you created.
- Code must pass `make lint` (gofmt-clean) and `make test` before it's done. CI runs exactly these checks.

## CI/CD (`.github/workflows/ci.yml`)

- On every PR or push, the lint job runs gofmt, vet, golangci-lint, build, the generated-code drift check (`make generate`, then `git diff --exit-code` and no untracked files) and `make api-lint`. The test job starts `postgres:16-alpine`, applies the migrations, and runs `go test -race` with `DATABASE_URL` and `TEST_DATABASE_URL` set to it, so integration tests run there instead of skipping.
- Every setup-go step uses `go-version-file: go.mod`, so CI runs the `toolchain` patch release (go1.27.3). **Bump the go.mod `toolchain` line and the Dockerfile builder (`golang:<tag>@sha256:...`) together**, so the source-mode scan checks the Go the image ships. The vulncheck job runs `make vulncheck` (govulncheck, pinned) and fails on vulnerabilities in reachable code.
- After lint-and-vet, test and vulncheck, the image job ("Build, Scan And Push Image") builds the image once (`load: true`, `VERSION` build-arg), scans it with Trivy (`aquasecurity/trivy-action` pinned by commit SHA, since its tags were force-pushed in 2026; fails on CRITICAL findings that have a fix, `ignore-unfixed`), runs `make vulncheck-image` (govulncheck `-mode=binary` on `/app/server` and `/app/import` copied out of that image), and only then pushes that same image. On PRs it stops before the push. Both `FROM` images in the `Dockerfile` are pinned by multi-arch index digest (`image:tag@sha256:...`); bump the tag and digest together (`docker buildx imagetools inspect`). The runtime runs as the non-root `app` user, and everything under `/app` is root-owned and read-only to it.
- On a push to `main` (or a tag), or a `workflow_dispatch`, the image is pushed to `ghcr.io/cosmofactory/recetas-backend` with the immutable tag `sha-<7>` (plus `vX.Y.Z` for a git tag). There is no `:latest`. The binary gets the same value via `-X main.version` and logs it at startup. There is no deploy yet; INF-2 adds it.
- In CI (`CI` set) `testdb` fails instead of skipping when `TEST_DATABASE_URL` is missing, so integration tests can't silently stop running.
- The CI test job sets `APP_ENV=local`.
